## 1. Summary
- RadixAttention keeps finished requests' KV in a radix tree so later requests reuse shared prefixes; LRU leaf eviction with per-node ref-counts; cache-aware scheduling (longest matched prefix first). [paper §3]
- In 0.5.20 the default tree for almost every model is now `UnifiedRadixCache` (`mem_cache/registry.py::default_radix_cache_factory` falls through to `_create_unified_radix_cache`): one tree with Full, SWA and Mamba *components*, each with its own lock counts and LRU, plus HiCache (L1 GPU, L2 host, L3 storage) as an attachment. [code]
- There is **no external pin/unpin/evict-this-prefix API**. The retention levers that exist are: session open/close (+ streaming sessions and a session-ref-aware tree), per-request `priority` with the `priority` eviction policy, eviction policy choice, HiCache tiers, and `flush_cache` (global, only when idle).

## 2. Problem and key insight
- Paper: prefix sharing across calls (few-shot, chat history, agent loops) is common; the tree gives automatic reuse without fixed slots; DFS-order scheduling is optimal for hit rate with cache >= max request length (Thm 3.1, §3) [paper]. Hit rate 50-99% on benchmarks, about 96% of optimal on average (Fig 13/App C); Chatbot Arena 52.4% (LLaVA-Next-34B) and 74.1% (Vicuna-33B), 1.7x lower first-token latency (§6.2); tree overhead below 0.3% (§6.3) [paper].
- The engine's objective is throughput/TTFT under memory pressure, not energy or task SLO; it has no notion of "the session is waiting on a tool".

## 3. Workloads
- Paper: LLM agents, few-shot, tree-of-thought, JSON decoding, RAG, chat; Llama-class models, A10G/A100 [paper; details not extracted]. No tool-wait or closed-loop agent traces. Hybrid blog: Qwen3-Next-80B-A3B FP8, H200, shared-prefix synthetic (50 groups x 10 prompts, 10240-token system prompt, concurrency 5) [blog].
- Nothing here is edge or agent-pause specific.

## 4. Assumptions
- Datacenter GPU; host tier is separate DRAM over PCIe; requests arrive continuously; prefix sharing is common. Default host pool sizing `hicache_ratio=2.0` (`hicache_hook.py::handle_hicache_ratio_default`) assumes plenty of RAM, and `host_memory_budget_bytes()` in `pool_host/base.py` uses `psutil.virtual_memory().available - 10 GiB` divided by ranks per host [code].

## 5. Controller / mechanism: inventory of control hooks (0.5.20)

### 5.1 Radix tree eviction
- `--radix-eviction-policy {lru,lfu,slru,priority}` (default `lru`); `--radix-eviction-policy-config` JSON, only `slru` takes `protected_threshold` (default 2) (`arg_groups/fields/memory.py`). Strategies in `mem_cache/evict_policy.py`: LRU = `last_access_time`; LFU = `(hit_count, last_access_time)`; SLRU = `(hit_count>=threshold, last_access_time)`; Priority = `(node.priority, last_access_time)`, lowest evicted first. FIFO/MRU/FILO classes exist but are not exposed as choices.
- `priority` only meaningful with `--enable-priority-scheduling` (docs). A request's `priority` stamps every node on its path on insert; node priority is the **max** over requests that touched it (`radix_cache.py::insert`, `unified_tree_core.py` lines ~1051-1203). It can be raised, never lowered, from outside. Unified-tree eviction order in `components/full.py` is `(session_ref>0, session_ref, strategy priority)` [code], so session-referenced nodes go last.
- `evict()` is a heap over evictable leaves; a freed leaf's parent joins the heap; hit counts do not increment for chunked-prefill steps or under write-back HiCache (docs).

### 5.2 Session APIs
- HTTP: `POST /open_session` (`OpenSessionReqInput{session_id, streaming, timeout, capacity_of_str_len}`), `POST /close_session`, and per-request `session_params{id, rid, offset, replace, drop_previous_output}` (`managers/io_struct.py`). Session tree of request nodes; idle `timeout` (s) closes it via `SessionController.maybe_reap` (1 s cadence) (`session/session_controller.py`).
- `--enable-session-radix-cache`: "track per-session references on UnifiedRadixCache KV: eviction consumes unreferenced entries before referenced ones, and closing a session only dereferences its KV". Implemented by `UnifiedSessionRefTracker` (`unified_cache/session_ref_tracker.py`): `register_session_ref` on finish, `release_radix_session` on close, per-component `session_ref`. This is a **soft pin scoped to open sessions**: a session's frontier leaf (and ancestors) survive until unreferenced KV is exhausted; it then can still be evicted. Requires the unified tree, otherwise the server raises (`registry.py::create_tree_cache`).
- `--enable-streaming-session` (`serving.py`): `StreamingSession` wraps the cache; each streaming session keeps a `SessionSlot` (its own `ReqKvInfo`: KV indices, mamba slot, SWA state) **outside the tree between turns** so the next turn reuses it with no match cost. It is held (not evictable) until close/timeout; metrics `sglang:num_streaming_sessions`, `sglang:streaming_session_held_tokens`. This is a **hard pin** with an idle TTL, and it costs pool capacity directly. `close_session` on a busy session is deferred (`close_on_finish`).
- No API to pin/unpin/evict an arbitrary prefix, list cached prefixes, or query one session's held size besides the two streaming metrics. `POST /flush_cache` flushes everything and returns failure unless `is_fully_idle()` (`scheduler.py::flush_cache`).

### 5.3 Priority scheduling and preemption
- `--enable-priority-scheduling` (requires `--schedule-policy fcfs|lof`, `validation_hook.py`), `--default-priority-value`, `--schedule-low-priority-values-first`, `--disable-priority-preemption`, `--priority-scheduling-preemption-threshold` (default 10 in `schedule.py`; the `PrefillAdder` constructor default is 0), `--abort-on-priority-when-disabled`. Per-request field `priority` in `GenerateReqInput`.
- `PrefillAdder.preempt_to_schedule` (`managers/schedule_policy.py` ~L1563): sort running reqs by `(priority, waiting time)`; a running request is preemptible if `(new.priority - running.priority) > threshold` (strict); enough victims must free the tokens needed; victims are released through `running_batch.release_req` and put on `preempt_list` (requeued). Cost model in section 5.4.

### 5.4 Retraction when the pool fills mid-decode
- Trigger: `scheduler.update_running_batch` (`scheduler.py` ~L4115): `not batch.check_decode_mem()` (allocator check for the next decode step, `ScheduleBatch.check_decode_mem`) -> `batch.retract_decode()`.
- Victim order `_get_decode_retraction_order` (`schedule_batch.py`): `--retraction-policy length` (default): the request with the fewest output tokens, then largest input, is retracted first (kept order sorted by `(len(output_ids), -len(input))` descending, popping from the end); `priority`: lowest priority first (same direction as scheduling), ties by length. Loop pops until `check_decode_mem` passes; always keeps at least one; if even one cannot fit it is aborted with "Out of memory even after retracting all other requests" (HTTP 500).
- What is recomputed: `release_req` calls `release_kv_cache(req, tree_cache, is_insert=False)` (the request's KV is freed and **not** inserted in the tree, source comment "we need the space instantly"; TODO comment about inserting) then `req.reset_for_retract()` clears prefix indices, locks, mamba slot and track buffers, `kv_committed_len=0`, `retraction_count += 1`. **`output_ids` are kept** (except with `input_embeds`), so on requeue the request re-prefills prompt+generated-so-far, reusing whatever radix-tree prefix still matches (its own KV is gone, but shared prefix may remain). Cost = one prefill of (prompt + decoded tokens), minus tree hits. It then evicts `remaining * SGLANG_RETRACT_DECODE_STEPS` (20) tokens from the tree to make room.
- **Host backup exists only in PD-decode mode:** `--disaggregation-decode-retraction-backup {cpu_tensor,host_pool}` copies KV plus Mamba state to host instead of recomputing (`release_req` gated on `disaggregation_mode == "decode"`). In monolithic mode retraction always means recompute.
- `new_token_ratio` (`NewTokenRatioTracker`): `init = min(SGLANG_INIT_NEW_TOKEN_RATIO(0.7) * --schedule-conservativeness, 1)`, `min = min(init * SGLANG_MIN_NEW_TOKEN_RATIO_FACTOR(0.14), 1)`, `decay = (init-min)/SGLANG_NEW_TOKEN_RATIO_DECAY_STEPS(600)`. `PrefillAdder` budgets each admitted request as `max_new_tokens * new_token_ratio` future tokens (`schedule_policy.py` ~L1225; requests with `ignore_eos` use 1.0). Each clean decode step `decay_step()`s the ratio down; after a retraction it jumps to `(sum(len(output_ids)) + SGLANG_RETRACT_DECODE_STEPS*n_reqs) / (sum(max_new_tokens)+1)` capped at 1.0. So admission is optimistic (0.7 of max_new_tokens decaying to 0.098) and a retraction storm is the price; a larger `--schedule-conservativeness` raises init and min. Metric `sglang:new_token_ratio`. **For 32K `max_new_tokens` thinking runs the estimate is very loose**; retractions are likely with many concurrent long decodes. [code; inferred consequence]

### 5.5 HiCache (hierarchical cache)
- Enable `--enable-hierarchical-cache`. Args (`memory.py`): `--hicache-ratio` (host/device pool ratio, default 2.0 in cache mode), `--hicache-size` (GB, overrides ratio), `--hicache-write-policy {write_through (default), write_through_selective, write_back}`, `--hicache-io-backend {direct, kernel (default), kernel_ascend}`, `--hicache-mem-layout {layer_first, page_first (default), page_first_direct, page_first_kv_split, page_head}`, `--hicache-storage-backend {file, mooncake, nixl, hf3fs, aibrix, eic, simm, mori, shm, sim, dynamic, ...}`, `--hicache-storage-prefetch-policy {best_effort, wait_complete, timeout (default)}`, `--hicache-host-memory-mode {cache, buffer_only}`, retry knobs (`--hicache-storage-prefetch-retry-*`, 8/8).
- Rules in `hicache_hook.py`: `page_first_direct` + `kernel` is rewritten to `direct`; `page_first` + `direct` is rewritten to `page_first_direct`. **On our driver, `kernel` fails and `direct` works**, so launch with `--hicache-io-backend direct` (layout auto-resolves to `page_first_direct`).
- Write policy semantics (docs): write_through copies to L2 immediately when bandwidth allows; selective writes after a hit-count threshold; write_back only on eviction. Prefetch policies control when an L3->L2 prefetch stops.
- Host pool is allocated with `cudaHostRegister` (`pool_host/common.py::alloc_with_host_register`, chunked by `SGLANG_HICACHE_HOST_REGISTER_CHUNK_GB`) or torch `pin_memory` (`alloc_with_pin_memory`); a Mamba host pool exists (`pool_host/mamba.py`), so HiCache is wired for hybrid models via `HybridCacheController` (`hybrid_cache/`). The **int8 mamba checkpoint and `--enable-unified-memory` are incompatible with HiCache** (`mamba_hook.py`, `memory.py` help text).
- HiCache metrics: `sglang:hicache_host_used_tokens`, `hicache_host_total_tokens`, `prefetched_tokens_total`, `backuped_tokens_total`, `load_back_tokens_total`, `load_back_bytes_total`, `hicache_backup_bytes_total`, `hicache_backup_duration_seconds`, `hicache_dropped_tokens_total`, `prefetch_bandwidth`, `backup_bandwidth`, `evicted_tokens_total`, `eviction_duration_seconds`.
- HTTP: `/hicache/storage-backend` (GET/PUT/DELETE, attach/detach L3 at runtime), `/hicache/storage-backend/clear`.

### 5.8 Hybrid models: what "retain vs recompute" means

#### 5.8.1 Mamba/Gated-DeltaNet (Qwen3.8)
- State is per-request and fixed-size; prefix reuse requires the state *at exactly the matched prefix length*. `MambaComponent` (`unified_cache/components/mamba.py`) matches to the deepest node where a Mamba value exists (or a host copy). Match returns a `mamba_branching_seqlen`: the last checkpoint-grid-aligned position inside the Full-KV hit that lies beyond the current Mamba boundary (`finalize_match_result_in_tree_core`), so the engine can create a new checkpoint at the branch on the next pass. Full KV may be reusable further than the recurrent state; the extra tokens must be recomputed through the SSM layers.
- `--mamba-radix-cache-strategy {auto,no_buffer,extra_buffer,extra_buffer_lazy}`: `no_buffer` needs `page_size` 1 and disables the overlap scheduler (`validate_mamba_no_buffer`); it donates the request's live state at finish (capped to the last flush boundary under ReplaySSM). `extra_buffer` keeps ping-pong track buffers per request and checkpoints in prefill on the chunk grid and during decode every `--mamba-track-interval` tokens (default **256**, must be a multiple of `page_size` and >= `speculative_num_draft_tokens`); `extra_buffer_lazy` holds one ping-pong slot and allocates the second only at a boundary (`mamba_lazy_prealloc_at_boundary`); not under PD-disagg. Checkpoint depths must land on `lcm(mamba_cache_chunk_size, page_size)` (`mamba_checkpoint_grid`), decode ones additionally on `lcm(that, mamba_track_interval)` (`mamba_track_grid`) [code]. `auto` picks `extra_buffer` when overlap or paging is wanted and the architecture supports it (Qwen3-Next, FalconH1, NemotronH per the search result), else `no_buffer` with overlap off (`overrides.py`).
- Sizing: `--mamba-full-memory-ratio` (default 0.9 fallback: mamba-state memory over full-KV memory), `--max-mamba-cache-size` (slot cap), `--mamba-max-states-per-path` (cap on cached states per root-to-tail path; -1 unlimited), `--enable-int8-mamba-checkpoint` / `--int8-mamba-ckpt-size`. Elastic pool (`--enable-unified-memory`) can move memory between Mamba and KV dynamically but not with HiCache.
- Eviction: Mamba states can be evicted from any node while Full KV goes leaf-first (two LRUs, blog); cascade rule: evicting a higher component drops lower-or-equal-priority components on the node (`unified_cache/README.md`).
- **Consequence for "retain vs recompute":** a paused session's reusable recurrent state exists only if a checkpoint was written at a grid position at or before the shared prefix. With a 256-token track interval, a retained state is at most 255 tokens stale from the boundary of interest, and a rebuilt prompt that diverges after the system prompt only reuses the checkpoint at or below the divergence; recompute cost is O(tokens after checkpoint). Cost of holding is a whole state slot per retained checkpoint (large; Marconi cites GB-scale for a 7B hybrid), so *fewer, well-placed checkpoints* beat a dense grid (Marconi's point).

#### 5.8.2 SWA (Gemma-4)
- Hybrid SWA pools split KV into a full-attention pool and an SWA pool (`--swa-full-tokens-ratio`, fallback **0.8**: SWA tokens per layer over full tokens per layer; `--disable-hybrid-swa-memory` turns it off; metrics `swa_token_usage`, `swa_*_tokens`, `max_total_num_tokens_swa`). The SWA component keeps a tombstone/window structure: a prefix match is valid for the SWA layers only if a contiguous window of the last W tokens is present (validator tracks "accumulated window length", `unified_cache/components/README.md`); SWA data can be evicted while Full KV remains (tombstone), forcing recompute of at most the window for local layers on partial hits.
- Consequence: retaining SWA state is cheap (bounded by the window per layer) versus global-layer KV growing with context; on Gemma-4 the retention cost is dominated by the few global layers. Recompute cost after loss of the window is bounded by W tokens of the local layers plus any global-KV loss [inferred].

#### 5.8.3 Marconi versus SGLang
- Marconi: admission only at branch points + last token, eviction by `recency + alpha*FLOPs/bytes`. SGLang: checkpoint on a fixed grid (prefill chunk grid, decode 256), LRU (or LFU/SLRU/priority) per component, cap via `mamba_max_states_per_path`. Closest mainline knob to Marconi's admission is `--mamba-max-states-per-path`; the FLOP-efficiency utility is not implemented and would replace `EvictionStrategy.get_priority` (Full) / the per-component LRU (Mamba).

## 7. What JouleServe-WS can take
Baselines and arms, each as launch flags (0.5.20):
- **B0 default:** `lru`, no session flags. **B1 retention by open session:** `--enable-session-radix-cache` + open/close_session around agent lifetime. **B2 hard pin:** `--enable-streaming-session`, open with `timeout=<T>`. **B3 priority-biased eviction:** `--enable-priority-scheduling --radix-eviction-policy priority --default-priority-value 0`, client sets `priority` per request (waiting sessions cannot be *re*-prioritized after the fact; a later request must carry it). **B4 preemption/retraction:** `--retraction-policy priority`, `--priority-scheduling-preemption-threshold`, `--schedule-conservativeness`. **B5 host offload:** `--enable-hierarchical-cache --hicache-io-backend direct --hicache-write-policy write_through_selective`, plus `--hicache-ratio`. **B6 LMCache** for the dense WS model.
- Tools to reuse: `/metrics` scraping (fields above), `sglang:num_retracted_*_total` to price recomputation, `estimated_flops` for FLOP-based utility, the `radix_cache_backend` plug-in for a research cache (Marconi-style utility, session-aware TTL) **without patching the engine**.

### 7.1 Where a sidecar can act without patching
- Session lifecycle: call `open_session` / `close_session` at agent-state transitions; use `timeout` as a TTL; toggle between "streaming" (hard pin) and non-streaming (soft pin) at open time.
- Admission control in front of the engine: hold or delay new requests based on `/metrics` (`token_usage`, `num_queue_reqs`, `new_token_ratio`, retraction counters). Per-request `priority`, `extra_key`/`cache_salt` (namespaces), `routing_key`.
- Abort (`/abort_request`) or pause (`/pause_generation`) long decodes; `flush_cache` when idle (coarse).
- Ordering of KV lifetime via *synthetic touches*: a cheap request with the session's prefix and `max_new_tokens=1` refreshes `last_access_time` (LRU) and re-stamps priority; costs one tiny forward each time; a workable "keep-alive" without a patch [inferred; untested].
- Attach/detach L3 storage backend at runtime via `/hicache/storage-backend`.

### 7.2 Where a minimal patch is needed
- Explicit per-session pin/unpin/evict-now/offload-now (needs a scheduler-side message like `open_session` carrying a `retain_class` and a hook in `UnifiedRadixCache`, the session tracker is the natural place: `UnifiedSessionRefTracker.release_radix_session` already releases by id).
- Lowering a node's priority; TTL-based expiry of tree nodes; "evict only if recompute cost < X" utility (custom `EvictionStrategy.get_priority`, one class, or a registered `radix_cache_backend`).
- Retraction victim choice by task value/energy (`_get_decode_retraction_order`), retraction-with-host-backup in monolithic mode (only PD-decode has it), and mutable scheduler knobs at runtime (`set_internal_state` allow-list).
- Per-session metrics (held tokens, hit tokens, retractions per session): none exist.

## 8. What JouleServe must add beyond it
- The decision layer: retain / soft-pin / hard-pin / offload / drop per session using expected tool-wait, reuse fraction, recompute cost (prefill FLOPs or joules), state size, and pool pressure. SGLang has mechanisms, not the policy.
- Energy accounting (Jetson rails, nvpmodel/DVFS-aware), task-level SLOs, and active-decode-aware admission (the new_token_ratio scheme assumes optimistic admission is cheap to correct; on a 25K-token pool with 32K thinking outputs it is not).
- Per-session observability and an external pin/evict control API.

## 9. Workstation to edge
- **Unified memory (the key point).** HiCache's "L2 host tier" is `cudaHostRegister`/pinned host memory sized from `psutil.virtual_memory().available - 10 GiB` (`pool_host/base.py`). On Jetson Orin/Thor host and GPU share one physical LPDDR pool (Tegra), so: (a) an L2 copy **does not add capacity**; it consumes the same DRAM that the L1 pool and the model weights use, so `hicache_ratio=2.0` would try to take 2x the KV pool from the same RAM (and the 10 GiB reserve is large on a 32 GB board); (b) "offload" is a DRAM-to-DRAM copy that competes for the same memory bandwidth as decode (decode is bandwidth-bound), so it costs time and energy with no freed capacity; (c) the only real capacity gains come from (i) storage-tier L3 (NVMe/file backend) which frees DRAM but is slow, or (ii) **compression/dropping** state (e.g. int8 Mamba checkpoints, `--enable-int8-mamba-checkpoint`, ~2x cached-prefix capacity per its help text, but incompatible with HiCache) or (iii) not holding at all. What remains of the host tier is accounting: freeing L1 pages for other active requests at the price of a pinned region elsewhere; net zero unless the L1 pool is statically sized smaller than what unified DRAM could give. The zero-copy possibility (GPU reading the host buffer in place) is not used by the `direct`/`kernel` paths [inferred; verify with a Jetson experiment]. Also: whether `cudaHostRegister` on a torch-allocated buffer on Tegra is a no-op or double-maps is not verified.
- Pinned host allocations on Tegra are not swappable, so an over-sized host pool starves the system; the 10 GiB reserve must be re-tuned.
- Thermal/DVFS and board power: no hooks in SGLang; must be measured externally (tegrastats/INA rails). Small batch: retraction/preemption dynamics differ; fewer concurrent requests but longer max lengths.
- Porting effort: flags port unchanged; the `kernel` io backend problem and `direct` fallback carry over (sm_87/sm_110 kernels are a risk); hybrid models (Gemma-4, Qwen3.8) route through `UnifiedRadixCache` on 0.5.20, so verify their exact model support in 0.5.20 before assuming.

## 10. Relevance to our current findings
- Retention gains bounded at 0.3-1.7% of LLM time in single-session traces; the engine's own machinery (LRU, retraction) is not the bottleneck there. Concurrency: active long decodes make `retraction` (recompute of prompt+decoded tokens, dropping the retracted request's own KV) the dominant memory-pressure cost. Priority/retraction-policy knobs are thus the **first** JouleServe lever, session pinning the second.
- Per-role rebuilt prompts mean the tree's shared prefix is the system prompt/tool schema only; open-session soft pinning largely pins tokens that will not be reused. Streaming sessions (hard pin) require append-only turns, which the rebuilt prompts violate (prompts differ per call) [inferred; check `Session.create_req` semantics].
